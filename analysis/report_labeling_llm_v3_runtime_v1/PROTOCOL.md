# V3 runtime integration protocol

This separately versioned implementation consumes the unchanged [v3 protocol](../report_labeling_llm_v3/PROTOCOL.md), prompts, definitions and pinned five-report preparation. It does not revise the experimental question, split, schema or framing policy. All 145 previously tracked analysis files except the analysis index are protected by SHA-256 at commit `babe7e7f4f576f300ca1ba035a2d6b6f80a6b857`.

## Execution boundary

GPU execution is hard-disabled in this revision, including the parent and standalone worker paths. Editing a Boolean or passing `--execute` cannot unlock it. A future reviewed source revision, current resource quote and explicit execution authorization are required. There are no downloads, provisioning calls, training steps or automatic retries. A CPU demo uses exactly five fabricated software fixtures and a fixed fabricated JSON response; it cannot consume competition reports or invoke the real factories. Its receipts are marked synthetic and measured-session verification rejects them by default.

The real preparation copies only the anchored candidate package and exact original 40/18 split membership to a new private folder. It verifies the original candidate-plan digest, all candidate code hashes, every copied artifact and fixed input digest. It recomputes both prompts from the original-language reports. It neither reads validation reports for inference nor changes labels. Every dispatch and review revalidates the plan, inputs and protected source files. No existing output is overwritten or resumed.

## Boundaries implemented for later execution

The parent dispatches four fresh subprocesses in ABBA order: control-1, candidate-1, candidate-2, control-2. Each process handles the same five reports in original order, maximum 20 generations and 240 condition cells. Workers require an inherited pipe, live parent PID, single-use dispatch nonce, session/plan binding and complete earlier child receipts. Completed sessions require every run, input identity/order, artifact checksum and exact response reparse to agree. Checksums detect accidental changes; they are not signatures against an operator deliberately rewriting all evidence.

The runtime reuses the frozen v2 offline model loader, cache auditor, encoder, token-preserving generator and process-group supervisor. It supplies a copied v3 model configuration without modifying frozen globals: pinned MedGemma revision, BF16, SDPA, batch one, greedy decoding, seed 20260914, input cap 8192, output cap 4096 and generation time cap 300 seconds. No thinking-disable flag is invented. The full pinned weight/config cache is audited before either real factory. Input size is checked before weight load; native BF16, all-CUDA BF16 parameters, SDPA configuration, revision, package versions and loaded context limit are checked before generation. Runtime receipts include actual hardware/driver/package metadata, effective settings, tokens, time and peak allocated memory.

Raw prompt text, rendered input, input/output token IDs, original decoded response and generation status are flushed and fsynced before response validation. Noncompleted generation stops the run and session. Completed parse/evidence failures remain visible; no repairs, retries or preferred-repeat selection. The shared frozen v3 validator accepts only its prospective strict leading thought envelope followed by the unchanged v2 lexical/schema/evidence checks. Positive / negative / uncertain / not_mentioned are preserved; not_mentioned never becomes negative.

Each worker is bounded by 1800 seconds, the parent session by 3600 seconds. The reused supervisor kills and reaps the process group on timeout or interruption. Graceful parent exceptions/interruptions produce failure receipts; SIGKILL or power loss can leave only partial durable files, which cannot pass the completed-session gate. No script claims provider shutdown: external operator stop and provider-state verification are required because killing a process does not stop billing. These are caps, not expected runtime estimates; the new GPU path has not been executed.

## Two-stage review

Only a verified complete session can create a review bundle. The explicit synthetic-demo override is required for fabricated sessions. The `blinded/` directory contains randomized opaque output codes, original reports, unchanged definitions, proposed labels/evidence, technical status, output hashes and a blank 240-cell review. It omits study IDs, run/arm mapping, prompts, thought text, generation timings and organizer references. The separate `operator/` directory maps codes to exact raw-record hashes and original runs; never serve or share it with the first-stage reviewer. Output wording and repeated reports can still reveal clues, so this is concealed assignment, not guaranteed perfect blinding.

First assess report entailment for technically valid cells. Record an identified reviewer, timezone-aware timestamp, output binding, nonempty category list and notes for issues. Categories permit polarity, anatomy/compartment, severity, temporality, unsupported negative, other entailment failure and insufficient information; `no_issue_identified` is exclusive. Technically invalid cells require exactly `technical_failure_unreviewable` and explanatory notes, with their technical reason retained separately. This administrative disposition is prohibited for valid cells and is excluded from semantic-error counts. It changes neither the extraction schema nor the frozen prompt/ontology. The initial stage excludes `reference_discordance`, because organizer answers are still concealed. Blank, partial, duplicate, stale, swapped or malformed reviews are rejected.

Only after all first-stage rows validate does the finalizer open the anchored organizer context and export a separate stage-two comparison. Numeric disagreement is descriptive; it does not decide which source is medically correct. Stage-two reference-review fields remain blank for a human. Review identity is self-reported; software cannot certify clinical qualifications. Existing 12 adjudication items remain unresolved. No result automatically authorizes scaling.

## Measurements and limits

Technical summaries retain per-run/per-condition attempted/planned denominators, failures, four-state distribution, binary coverage and paired repeat differences in label/evidence/offset/status. Unreviewed semantic accuracy is null. Post-review summaries separately count technical acceptance, unreviewable technical failures, the technically valid semantic-review denominator, reviewer no-issue yield, reviewer no-issue binary yield, human semantic error categories and conditional organizer agreement. Technical failures never contribute semantic-error categories or semantic passes. Do not equate an accepted nonmention with a correct binary label.

No actual v3 outputs exist. Demo counts exercise accounting only and are not model performance. This integration does not implement a scaling gate, clinical certification or a complete future scientific results dashboard. The study-level token/latency records remain available for later real analysis. The five studies are the independent units; repeats and condition cells are correlated. Four English reports and one Spanish report cannot establish multilingual reliability. The 18-study validation set is unused by this runtime and is too small for strong condition-specific reliability claims.
