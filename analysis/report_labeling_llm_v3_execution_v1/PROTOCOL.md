# MedGemma v3 execution proposal

This is a prospective, authorization-gated execution revision of the completed [local runtime](../report_labeling_llm_v3_runtime_v1/README.md). All 156 prior analysis files are checksum-protected at `0353ecb880fd9bc20a78c602508ff7152a7d5ad5`, including that hard-disabled runtime. Its source and historical preparations are not edited. The runner/reviewer are versioned copies with unique module names to preserve separate configuration, fingerprints and review behavior.

## Unchanged experiment

The frozen [v3 protocol](../report_labeling_llm_v3/PROTOCOL.md) applies: five previously inspected development reports, original languages/order, exact 40-development/18-validation membership, MedGemma only, control-1 → candidate-1 → candidate-2 → control-2, maximum 20 generations. Exact model `google/medgemma-1.5-4b-it` revision `91850547d9f0b2fdd21aa7c5f4f3d1a8a52c243b`; all ten existing package pins, BF16, SDPA, batch one, greedy, seed 20260914, 8192 input / 4096 output tokens and 300 seconds per generation. No prompt, definition, response framing or model-label changes. No training, Qwen, validation inference, full-development inference or bulk labeling.

The four-state extraction schema remains positive / negative / uncertain / not_mentioned, with evidence and confidence; never map not_mentioned to negative. Frozen lexical validation cannot certify semantic correctness. Technically invalid cells require only the non-semantic review disposition `technical_failure_unreviewable`; valid cells require the original human semantic categories. First-stage review conceals organizer references and assignment; stage two remains separate. `reviewed` means workflow-accounted cells, while `semantically_reviewed` is the valid-cell semantic denominator. All 12 earlier adjudications remain unresolved.

## Authorization and spending boundary

This source can execute real inference only with `--execute`, the exact reviewed runtime-plan SHA, a private plan/proposal-bound approval record and a live pod-local self-stop watchdog. No actual approval is included in Git or created by preparation. Missing, false, expired, mismatched, publicly readable or over-budget records fail before model imports/loading. Both parent and worker enforce the gate. Synthetic plans cannot authorize real models, and fabricated sessions remain rejected as measured outputs by default.

The [resource proposal](configs/resource_proposal.json) covers restarting the existing stopped RTX 6000 Ada 48 GB pod, one GPU, 80 GB temporary container disk, no new persistent volume. Console restart quote: $0.84/hour compute. Historical identical disk rate and current public pricing imply about $0.011/hour storage; confirm the actual displayed storage rate before starting. Proposed experiment budget: **$2**, provider window **at most 90 minutes from the start request**, including setup/downloads/results transfer. At $0.851/hour, 90 minutes is approximately **$1.28**. These are estimates, not a provider-enforced dollar cap; existing storage charges are separate. Capacity is not guaranteed by the presence of a Start button. No substitute GPU, new volume, repeated provisioning attempt or automatic budget extension is included.

The proposal expires after 24 hours. Record actual approved rates and timestamps, the exact pod identity, user approval reference and private grant. Runtime rejects compute/storage rates above the proposal, estimates exceeding the approved budget, windows over 90 minutes, or insufficient time for the five-minute copy/stop reserve. The parent reduces its worker deadline to the earlier of the original 60-minute session limit and that reserve. Worker hard cap remains 30 minutes. Noncompletion stops dispatch; partial results cannot pass the paired comparison. Worst-case 20 × 300 seconds exceeds the session cap, so completion is not guaranteed and no automatic retry or extension is permitted.

## Operational sequence after approval

1. Recheck the console quote and exact target, capture the start-request time, and start only the approved stopped pod. Record the actual allocation and current charges. Stop if capacity, hardware or price differs from the proposal.
2. Establish SSH and verify the official image, Python/CUDA/runtime pins and native BF16. Verify the installed `runpodctl` help syntax and read-only access to this pod using its existing provider-scoped authentication. Do not copy credentials into project files or logs.
3. Launch the detached self-stop watchdog immediately with the absolute approved deadline and observed modern or legacy CLI syntax. It can target only `RUNPOD_POD_ID`; its PID, script checksum, target and deadline must match the private authorization. The runtime checks its live Linux process identity. Keep external operator monitoring as a fallback.
4. Restore the exact private prepared package. Re-download only the pinned MedGemma snapshot if the temporary cache was cleared, roughly 8.60 GB of weight files plus tokenizer/config files. Do not fetch MRI images or Qwen weights. Audit every required cache file before each run. The inference worker remains offline.
5. Run once with the reviewed SHA and approval/watchdog files. Actual GPU name must match the proposal; revision, hardware, packages, input sizes, full-cache bytes, context size and parent/worker provenance checks apply. Raw output is durable before parsing. Parent snapshots the approval/watchdog evidence and preserves it for offline verification.
6. Copy durable outputs locally during/after execution, verify checksums, and explicitly stop the pod on completion or failure. Independently verify provider stopped state and charges. The watchdog is a backstop, not permission to leave compute running until its deadline. Its successful CLI request alone does not prove provider billing stopped. If the API/CLI stop fails, the external operator must stop through the console. Temporary disk can be erased on stop; prioritize ongoing result transfer and leave the five-minute reserve.

The watchdog makes at most three bounded stop attempts, with no inference retries. Its implementation and CPU tests do not prove the provider API will succeed; installed CLI capability/access and actual remote process liveness must be checked after boot, before inference. No provider start, stop or authentication call is performed by CPU tests.

## Expected timing and remaining limits

Earlier MedGemma calls took 75–92 seconds at the 2048-token cap. With 4096 available, **roughly 30–60 minutes for the session**, plus perhaps 10–20 minutes setup and a few minutes transfer, is a planning estimate only. New output lengths, setup downloads and cache timing have not been measured. A new model-response failure can stop much earlier. The 60-minute inference and 90-minute provider limits remain controlling even if the expected comparison is incomplete.

Qualified semantic review, organizer-reference adjudication and any scaling decision occur locally after verified transfer. Five studies are the independent units; four English/one Spanish is descriptive only. The 18-study holdout is not used or tuned on and remains too small for strong per-condition reliability claims. No v3 accuracy, improved labels or clinical qualification is claimed from software tests.
